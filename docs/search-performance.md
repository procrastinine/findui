# Search execution and performance

[FindUI](../README.md) · [Documentation](../README.md#documentation)

How FindUI chooses execution plans, shares work, and measures tradeoffs. See [search architecture](search-architecture.md) for the module boundaries.

See [backend selection](backend-selection.md) for the execution tools and repeatable comparisons against `ugrep`. The benchmark checks complete result sets and includes streaming/recursive inputs so argument-list overhead does not decide the comparison.

- Compound content conditions share one read of each candidate. Duplicate conditions compile once. A combined regex prefilter skips irrelevant blocks, and a bounded worker pool searches different files concurrently. Same-line and same-file Boolean semantics, including negation and empty files, remain distinct.
- **Rules** uses one nested AND/OR/NOT tree. Change a row's type to filename, contents, size, date, tags or another condition; file and content conditions can share a branch. For example, `((Swift AND TODO) OR (Markdown AND FIXME)) AND modified this week`. Separable trees retain native fd/rg plans; mixed trees check file conditions before one shared content scan and return matching files once. See [the rules contract](search-query-ui-contract.md).
- Simple searches execute fd or rg directly. Eligible basename/extension + contents combinations use one rg traversal with type filters, preserving ignore rules. Compound conditions use a shared parallel walk and scan, with one matcher per distinct condition. Files-only searches stop when the Boolean answer is certain. **Scope & Options → Advanced → Search workers** sets 1–64 workers; automatic worker execution uses at most 12. Native fd/rg keep their scheduling defaults unless overridden. Conversion concurrency is capped at four and respects lower worker counts.
- Fuzzy content searches preserve `fzf` rank during parallel scanning. Later files wait in bounded buffers (at most 1 MiB of match text per worker in memory, then temporary storage); the file whose turn it is can stream immediately. Ordinary unranked searches stream in completion order.
- Compound filename conditions share a metadata lookup. Cheap filters run before fuzzy ranking and content reads. General fuzzy Boolean groups join real fzf results in bounded temporary storage; no per-branch file traversal or content scan is needed.
- Presentation metadata is loaded once per matched file per execution. Index builds enumerate files and directories together. Fresh searches still read current content/metadata; live filename lists are never silently reused between searches.

Filename snapshots store compiled query records and metadata in SQLite. A normalized trigram index narrows suitable name/path queries before the shared predicate verifies them; short, broad, Unicode-sensitive and unsupported patterns retain a scan fallback. Refresh commits only changed rows, with no full natural sort or JSON rewrite. Query preparation freezes one consistent generation using an APFS copy-on-write clone (ordinary copy on other filesystems); readers fetch display metadata only for matches. Both GUI and CLI load the small header without decoding every entry. The Settings inspector loads 200 entries per page, with cancellable filtering. Leases protect active generations during refresh. Legacy JSON snapshots remain readable, and `index export` produces inspectable JSON. Snapshot searches support the same `--print-command`, `--explain-plan` and `--stats` actions as live searches.

**Scope & Options → Advanced → Prepare Content Index** prepares conservative four-gram signatures for documents and text files of at least 256 KiB. Smaller text files are cheaper to scan directly. Enable **Use content index** to reuse these signatures; preparation enables it for the current search. The default is off so ordinary searches remain native rg commands. Changed files are scanned and refreshed. Building signatures is an explicit cost rather than a slowdown on every first search. Suitable regexes reuse bounded required-literal signatures. Short literals, optional/unsupported regexes, unsupported case folds and encodings fall back to scanning. Binary records have integrity checks; missing or corrupt records cannot exclude files, and cache failures fall back to searching. Filesystems with coarse timestamps bypass reuse. This is a conservative skip index, not a word-token full-text database; the existing matcher still verifies every candidate.

`ruby scripts/benchmark_content.rb` compares the compound worker with four separate single-threaded `rg` scans, excluding their later merge cost. The benchmark uses synthetic fixtures and warm caches. Measure representative queries on your own storage before drawing conclusions about performance.

Result pages retain bounded sort indexes and reuse the visible page while its membership stays unchanged; CSV export uses one ordered cursor. The first batch appears promptly, later updates are coalesced, and completion always publishes the final batch. Storage failures stop the producer. Content groups show document-wide counts and navigate across page boundaries without loading all matches into the view. Highlight offset conversion scans UTF-8 once; long snippets display bounded windows with Previous/Next highlight controls while copying and export retain the full result. **Scope & Options → From Results** suggests types, folders, dates and available tags, applying the same additive filter logic as presets. Tags already read for filtering are retained; otherwise tag facets load them only when requested. Indexed-word suggestions use the native search menu and prepared vocabulary/history; accepting one changes the shared query state.

SHA-256 uses RustCrypto's runtime hardware detection. Cache serialization batches tiny JSON writes into a bounded 64 KiB buffer before gzip compression. Format recognition is cached under validated document/archive identities, and word updates avoid repeated root resolution, irrelevant WAL probes and unchanged alias/membership writes.
